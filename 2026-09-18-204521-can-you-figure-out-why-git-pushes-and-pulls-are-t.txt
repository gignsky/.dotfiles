  Strip those four and the pack drops to roughly 8 MB.

  Why they're still there

  Two separate mistakes, same outcome.

  The tarball: 630b4284 added a 59 MB tarball of cargo binaries. b16bb741
  removed it, replacing it with a text listing — the right call, and the commit
  message shows the intent was always documentation, not the binary. But
  deleting a file in a later commit doesn't remove it from history. The adding
  commit is still reachable, so the blob can never be garbage-collected.

  The wallpapers: these were committed raw, and LFS was adopted afterward
  (9f99c2f2 tracking .png for git lfs). This is the classic LFS trap — editing
  .gitattributes only changes how future commits are stored. It never rewrites
  what's already there. So you now have both copies:

  history:      31.2 MB raw blob  (pre-LFS commits, permanently reachable)
  .git/lfs:     32 MB LFS object  (post-migration)
  HEAD:         133-byte pointer

  Those three images are stored twice — ~112 MB of disk for ~57 MB of actual
  pictures. git lfs migrate would have been needed to rewrite history; git lfs 
  track alone was not enough.

  Being honest about scope, because this is the part that's easy to overstate:

  - It does not slow down your day-to-day push/pull. Git only transfers objects
  the other side lacks. Your 10-second push delay is the DNS problem, not this.
  Fixing the bloat would not have made pushes faster.

  Why the blacklist was the wrong instinct

  Beyond redundancy — search gignsky.com is not the bug. It's the feature you
  want. It's what makes ssh merlin work. The bug is a search domain pointed at a
  zone that can never say "no". Blacklisting would have deleted the feature to
  work around the defect.

  For the local domain later

  The combination you want is a search domain over a zone that returns NXDOMAIN
  for names that don't exist. The lever is making your Pi-hole authoritative for
  an internal zone rather than forwarding it upstream — in dnsmasq terms:

  local=/lan.gignsky.com/                          # never forward; NXDOMAIN if
  no local record
  host-record=merlin.lan.gignsky.com,192.168.51.x

  That local= line is the crux. Without it the Pi-hole forwards to Cloudflare
  and the wildcard answers. With it, github.com.lan.gignsky.com gets a clean
  NXDOMAIN and glibc falls through correctly — while merlin still resolves. Then
  set DHCP's search domain to lan.gignsky.com.

  Two things worth weighing:

  - Why a subdomain of a domain you own beats .internal or .lan: you can issue
  real Let's Encrypt certs for internal-only services via the Cloudflare DNS-01
  challenge, without exposing anything. Made-up TLDs can't do that.
  - The alternative — dropping the wildcard at Cloudflare for explicit
  per-service records — gives you honest DNS everywhere, at the cost of a record
  per service. Better hygiene; more upkeep. If the wildcard is earning its keep
  with a reverse proxy, the local= approach keeps it.
